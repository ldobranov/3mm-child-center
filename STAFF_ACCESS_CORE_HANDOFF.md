в локален Core b3154f9. Child Center 0.6.6 използва този endpoint за Operator

Core/Agent/аппът не са променяни. Runtime версията остава 0.6.5.

## Проверено поведение

Използвани са текущият Child Center contract и реалните платформени HTTP
проверки с временна база. Извикването на supervised service е заменено с
тестов запис след проверката на правата; не са извършвани бизнес операции.

- Директните grants са върху User + application installation + permission.
- Operator gateway проверява актуалните grants за всяка заявка. Отнемането
  спира следващата заявка със същия токен преди достигане на service.
- Рецепция без payments_manage не може да изпрати плащане или сама да си
  даде права. Обикновен потребител не може да чете списъка с чужди grants.
- Operator desk route изисква едновременно registrations_manage,
  children_manage и visits_manage. Рецепция само с първите две няма достъп.
- configuration_manage/ privacy_manage не правят служителя администратор:
  administrator route и admin operation gateway изискват глобален admin.
- User има и Role/Group отношения, но провереният application_permission_ids
  resolver чете само директни ApplicationPermissionGrant записи. Не използва
  тези отношения. Това не е пълен одит на всички права в останалия Core.
- Не е намерен публичен за автентикирания служител договор за собствените му
  разрешени extension операции. GET /permissions е admin-only; каталогът
  филтрира routes, но не предоставя пълните оперативни права на компонентите.

Локални източници: backend/services/application_access.py;
backend/routes/application_extensions.py (operator gateway и permissions);
backend/db/user.py; modules/child-center/application-extension.json.

## P0: минимална необходима обща промяна

Добавете read-only endpoint за собствен достъп, например:

`GET /api/v1/application-extensions/{module_id}/access`

Предложен строг отговор:

```json
{
  "module_id": "org.example.application",
  "active_version": "1.0.0",
  "user_id": 42,
  "allowed_route_ids": ["desk"],
  "allowed_operation_ids": ["list_records"]
}
```

Имената и URL са предложение за съгласуване, не frontend dependency засега.
За UI са нужни разрешените операции, не списък с потребители или собствено
тълкуване на `role=admin`. Решението трябва да идва от същите server policies,
които действително разрешават routes/операции, включително audience и admin
правилата. Не може просто да се върнат всички декларирани permissions.

Изисквания:

1. Само текущият автентикиран човешки потребител; без избор на чужд user_id.
   Kiosk, anonymous и device credentials не получават служебен access snapshot.
2. Проверка на активната инсталация/версия. Disabled или unavailable не връща
   старо разрешение; грешките и празният разрешен списък са различими.
3. Cache-Control: no-store. UI обновява при вход, смяна на потребител, връщане
   на фокус и отказ 401/403. Snapshot не е токен и не разрешава мутации сам.
4. Преизползване на общ resolver/policy, без имена или роли на Child Center.
   Директните grants и поведението на съществуващите клиенти се запазват.
5. Тестове: никакви grants, частични grants, admin, отнемане със същия токен,
   други инсталации, disabled extension и отказ за kiosk. Snapshot и gateway
   трябва да дават съгласувано решение. Проверете и политиката за блокиран
   потребител/отнета сесия; тя не беше доказана от настоящите шест теста.

Това е единственият непосредствен Core blocker за permission-aware Operator UI.
Не са нужни хардуерни промени или цялостно пренаписване на role системата за P0.

## След P0: промени само в Child Center

- Чете собствените allowed operations; не декодира JWT за авторитетни права,
  не чете Core DB и не пробва мутации, за да установява достъп.
- Разделя наличността на tabs, данни и действия. Не прави заявки за забранени
  данни при mount на скрит компонент. При грешка затваря действията безопасно.
- Преглежда route prerequisites: достъпът до общ desk не трябва да изисква
  всички оперативни права наведнъж. Решението се прави с изричен минимален
  desk grant или разделени routes, според наличния общ contract; без отваряне
  към anonymous/public и без премахване на operation authorization.
- Платежните действия се виждат само при право за тях. Cashier-only профил
  изисква и отделяне на account read от широкото visits_manage, което днес
  позволява и приключване на играта. Това е extension contract промяна.
- Ако разделим разрешения, подготвяме upgrade карта за съществуващите grants,
  без автоматично добавяне на финансови/административни права. Уточняваме
  платформения механизъм за такъв upgrade преди смяна на contract-а.

## Целева матрица — предложения за приемане

| Действие | Рецепция | Оператор на залата | Касиер | Управител |
| --- | --- | --- | --- | --- |
| Регистрация / одобрение / гривни | Да | Само при допълнителен grant | Не | По изрично зададени права |
| Престой / пауза / край на играта | Не | Да | Не | По изрично зададени права |
| Консумация | Не | Да | По допълнителен grant | По изрично зададени права |
| Преглед на сметка / плащане | Не | Без плащане | Да | По изрично зададени права |
| Конфигурация на центъра | Не | Не | Не | Целево да; отделна P1 зависимост |
| Експорт / изтриване | Не | Не | Не | Само отделно изрично право |

Това не са текущи готови роли. Служител може да съчетава няколко комплекта.
Никой комплект не дава автоматично управление на потребители или глобален admin.

## P1: последващи общи решения, не блокери за първия UI етап

- Обвързване на generic extension permissions с наличните роли/групи. Един
  resolver за gateway, route catalog и access snapshot. Дефинирайте как се
  събират grants и как се отнемат; без собствена role система в extension-а.
- Делегирано конфигуриране без global admin: нов/уточнен общ договор, който
  отделя application configuration от install, secrets, grants и други
  платформени администраторски функции. Не отслабвайте require_admin глобално.
- Проследимост при grant/revoke, lifecycle и restore; запазване на инициатора
  на фонова команда. Отнемането не трябва да повтори или загуби вече приета
  финансова заявка. Допълнителни тестове са нужни преди такива промени.
