# Core: разграничаване на неизпратена задача от неизвестно изпълнение

Дата: 2026-09-15. Задание за отделната Core задача; тук не е променяно ядрото.

## Установен инцидент

Часове по Europe/Sofia от systemd и durable job state:

- 15:34:10 — application extension host е спрян при системно обновяване.
- 15:34:51 — Core стартира.
- 15:34:52 — планировчикът опитва job; резултатът е `unknown / execution_unconfirmed`.
- 15:38:00 — application extension host стартира отново.
- Блокиращият lease остава след старта и последващия upgrade на extension-а.
- Нов прием от 19:30 остава `prepared`, защото задачите на инсталацията са блокирани.

Проверка само за четене към Barsy мина успешно с HTTP 200. Не е повторение
на грешката при декриптиране. Потребителят потвърди, че в Barsy няма операция.
Предходните финансови команди в extension базата са confirmed; не са преигравани.

Логовете доказват опит за задача, докато host услугата е спряна. Durable записът
не пази конкретната транспортна фаза, затова последващата автоматична класификация
на този стар запис като definitely-not-sent не е допустима само по error_category.

## Причина в договора за грешките

`backend/services/application_jobs.py:execute_job` превръща всяко изключение
от `invoke_application` в неизвестно изпълнение с блокиращ lease.

`three_mm_runtime/application_transport.py:ApplicationServiceClient.invoke`
обединява грешки при connect, изпращане и четене в обща транспортна грешка.
`backend/services/application_extensions.py` предава само общото описание.

Отказ на connect преди изпращане не може да е изпълнил тази заявка. Загубен
отговор след изпращане обаче може да е след реална външна мутация. Тези случаи
трябва да останат различни по целия transport → gateway → scheduler път.

## Необходима поправка

1. Добавете структурирана, типизирана информация за dispatch фазата.
   - `not_dispatched`: доказано не е започнало изпращане на заявката към host-а.
   - `execution_unconfirmed`: изпращането е започнало или резултатът не е надежден.
   - Не класифицирайте по текст на exception и не се доверявайте на произволна
     грешка, върната от extension-а, като доказателство за липса на ефект.
2. При доказано неизпратена временна грешка освободете само притежавания claim
   чрез CAS и отложете задачата с ограничен backoff. Запазете договорената
   идентичност на неизпратеното изпълнение; без лавина от пропуснати ticks.
3. След началото на send, включително partial send, read timeout, невалиден
   подпис/отговор, загубен отговор или провал на output validation, запазете
   консервативната quarantine и служебното разрешаване.
4. Преди dispatch проверявайте lifecycle/готовността на host-а. Само `active`
   в базата или съществуващ socket файл не доказват готовност. Проверка за
   readiness не заменя правилната обработка на race при самия connect/send.
5. При стартиране/обновяване на системата не подавайте работа към host, който
   още не е готов. Не добавяйте фиксиран sleep като единствено решение.
6. Поддържайте ownership, bounded concurrency, disable/upgrade/restore fencing,
   стабилни idempotency IDs, физически deadlines и generic Core.
7. Показвайте отделно „чака услугата“ и „неясно изпълнение — нужна проверка“.
   Без лични данни, credentials, тела на заявки или сурови exception съобщения.

## Тестове за приемане

- Core стартира преди host-а: няма вечен unknown lease; след реална готовност
  задачата се изпълнява веднъж без ръчна намеса.
- Socket липсва и socket съществува, но connect е отказан: bounded backoff,
  not_dispatched, без външна мутация и без блокиране на други приложения.
- Host спира между readiness проверката и connect: същото безопасно поведение.
- Грешка по време на send / partial send / загубен отговор след приета заявка:
  unknown остава блокирано, без автоматично повторение на финансови действия.
- Невалиден output след изпълнение не се третира като not_dispatched.
- Два планировчика, дълга задача, restart, upgrade, disable и restore не
  допускат дублиране или освобождаване на чужд claim.
- Старите unknown записи НЕ се отключват масово чрез миграция или по timeout.
- Интеграционна проверка през реалния Unix socket клиент, не само mock на gateway.

## Възстановяване на конкретния инцидент

Използвайте съществуващия администраторски API за job resolution с изключена
инсталация и потвърден външен резултат. Без SQL изтриване на lease и без
автоматично преиграване на финансови команди. Преди повторно включване уточнете
дали старият чакащ прием трябва да се отмени или да продължи: повторното включване
може да отвори сметка по този прием. Потребителското решение още се очаква.

## Граница на extension-а

Extension-ът не работи, докато host услугата е спряна, и не може сам да предотврати
този Core dispatch отказ. Не добавяйте в него автоматично отключване на Core jobs
или заобикаляне на неизвестен финансов/физически резултат.
